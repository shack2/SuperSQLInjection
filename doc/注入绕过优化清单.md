# SuperSQLInjectionV2 注入绕过子系统优化清单

> 基于 Bypass/ 全部源码（BypassPipeline / BypassPlan / StringReplace / ScriptTamperEngine / QuickJs / EncodeToolRegistry / BuiltinTampers）、HTTPTool 调用点、ByPassConfig 失效机制逐项核查整理（2026-09-28）。
> 每项包含：为什么优化（现状与问题）、如何优化（具体方案与落点）、是否建议优化（结论与优先级）。

## 优先级定义

| 级别 | 含义 |
| --- | --- |
| P0 | 热路径纯收益，无行为变化，低风险，建议直接做 |

## 一、性能优化

### 1. 标记短路：无标记报文跳过正则匹配【P0 · 建议】 ✅已实施

- **为什么**：`StrReplaceCenterAsync` 每请求无条件执行 3 个正则（`SencondDirectiveRegex` 指令提取、`RandBlockRegex` 替换、`EncodeBlockRegex` 块匹配）。盲注逐字符高并发时，绝大多数报文不带 `<Sencond:` / `<Rand>` / `<Encode>` 标记，仍白付 3 次全文扫描 + MatchCollection 分配。Stage1 的 Token 已有 `Contains("<Token")` 短路先例，这三处没有对齐。
- **如何优化**：落点 `Bypass/StringReplace.cs` 第 69 / 107 / 114 行。三处分别加前置判断：`Contains("<Sencond:", Ordinal)`、`Contains("<Rand>", Ordinal)`、`Contains("<Encode", Ordinal)`，不含标记直接跳过对应正则。
- **是否建议**：✅ 建议。纯收益、零行为变化（Contains 与正则前缀一致），改动约 10 行。

### 2. RandCache 命中路径免锁、免重复入队【P0 · 建议】 ✅已实施

- **为什么**：当前逻辑 `TryGetValue` 命中后，仍进入 `lock` 执行 `cache[body]=rand`（无效重赋值）+ `Lru.Enqueue(body)`（重复键入队）。两个问题：① 每请求一次全局锁竞争，高并发盲注下成为串行点；② LRU 队列被重复键膨胀（cap=500 时队列远长于字典），真实条目被加速淘汰，幂等性保护窗口缩短。
- **如何优化**：落点 `Bypass/StringReplace.cs` 第 87-105 行。命中分支直接复用 rand 并跳过锁内重排（近似 LRU 即可，幂等性不受影响——同报文始终映射同一值）；仅 miss 分支进 lock 做插入 + 入队 + 淘汰。
- **是否建议**：✅ 建议。锁竞争消除 + LRU 语义更准，行为对外不变。

### 3. QuickJS 函数句柄缓存【P0 · 建议】 ✅已实施

- **为什么**：`QuickJsContext.CallCore` 每次调用都执行 `JS_GetGlobalObject` + `JS_GetPropertyStr("tamper")` 两次原生互操作，盲注逐字符 × 编码链多工具时每天发生数万次。函数在 Load 后即固定，查找纯属重复。
- **如何优化**：落点 `Bypass/QuickJs/QuickJsContext.cs`。在 `Load` 成功后解析并缓存 `tamper` 的 JSValue（注意持有引用计数，Dispose 时释放）；`CallCore` 直接使用缓存句柄，省掉每调用的 global 获取与属性查找。
- **是否建议**：✅ 建议。微优化但热路径调用频次极高，实现约 15 行，风险仅在于正确管理 JSValue 引用计数（已有 FreeValue 封装可复用）。

### 4. 限速状态进程级 static → 收归 AppConfig 实例【P1 · 建议】 ✅已实施

- **为什么**：`_throttleSem` / `_lastSendTime` 是 static，全进程共享。与本轮架构方向（RandCache/LastToken/LastRand 已全部收归 AppConfig 实例）不一致；多目标/多任务并发扫描时，不同目标互相占用限速时间槽，语义错误。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` 第 214-248 行。把 `_lastSendTime` 与信号量移为 AppConfig 实例字段（JsonIgnore），`ApplyFreqAsync` 改从 `request.AppConfig` 取。
- **是否建议**：✅ 建议。当前单目标 UI 场景无感知，但属一致性债，改动小。

### 5. ApplyHpp 动态正则预编译【P1 · 建议】 ✅已实施

- **为什么**：每请求 `Regex.Match(txt, "(?<pre>[?&]" + Regex.Escape(pname) + "=)...")` 现场拼接模式串，依赖 .NET Regex 运行缓存（默认 15 条）兜底；参数名变化或多目标交替时缓存抖动重建。且该正则未走源生成。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` 第 324 行。注入参数名在一轮任务中固定，可按 pname 键控缓存编译好的 Regex（小字典，或纳入 BypassPlan 构建——pname 取自 DataConfig，需注意其变更也要递增 Revision，否则独立键控缓存更简单）。
- **是否建议**：✅ 建议（键控缓存方案）。收益中等但实现简单；纳入 Plan 的方案牵扯 Revision 联动，不建议为这一项做。

### 6. FixContentLength 无报文脚本时跳过第二次调用【P1 · 建议】 ✅已实施

- **为什么**：`StrReplaceCenterAsync` 末尾已收敛一次 Content-Length；`ApplyOnceAsync` 在 Stage3 后无条件再收敛一次。当 `plan.RequestTools.Length == 0`（绝大多数配置）时 Stage3 不可能改写报文，第二次是全报文扫描的纯浪费。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` 第 48-50 行。`ApplyRequestScriptsAsync` 返回 bool（是否实际执行了工具链），或直接在 ApplyOnceAsync 中判断 `plan.RequestTools.Length > 0` 才调 FixContentLength。
- **是否建议**：✅ 建议。一行条件判断，省去每请求一次头区扫描 + body 字节计数。

### 7. 单 context 池化锁 → 每脚本小池【P2 · 可选】

- **为什么**：同一脚本所有线程共用 `pooled.Sync` 串行执行（QuickJS context 非线程安全的正确设计）。脚本本身微秒级时无碍；但签名类重脚本（毫秒级）+ 高线程盲注时，N 个线程退化为串行，吞吐量被脚本拖平。
- **如何优化**：落点 `Bypass/ScriptTamperEngine.cs` PooledContext。每脚本键下挂 2~4 个 context（按 ThreadSize 或固定 4），轮询取用各自加锁；池上限 MaxPoolSize 按 context 总数计。
- **是否建议**：🔶 可选。先用日志实测脚本执行耗时占比，确认是瓶颈再做；context 有原生内存开销（16MB 上限/个），不宜无限扩。

### 8. 多标记名 Token 并行抓取【P2 · 可选】

- **为什么**：`ReplaceTokenAsync` 按标记名分组后串行 await，多个不同 `<Token:tag>` 意味着多次 HTTP 往返串行叠加，主请求延迟 = 各抓取之和。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` 第 161-186 行。分组抓取改 `Task.WhenAll`，结果汇合后统一做块替换（替换本身是内存操作，顺序无关）。
- **是否建议**：🔶 可选。多标记名同报文是少数场景，且并行增加目标瞬时压力；实现时注意每组写入 `config.LastToken` 的语义（现行为最后一组覆盖）。

### 9. ApplyRandomUa 双趟扫描合并【P2 · 可选】 ✅已实施

- **为什么**：先 `IsMatch` 再 `Replace`，同一正则对报文头区扫描两趟。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` 第 293 行。改为 `Match` 一次判成功再 Replace（或 MatchEvaluator 直替）。
- **是否建议**：🔶 可选。头区短、开销小，顺手可改。
- **实施记录**（2026-09-28）：`Match` 单次扫描 + `string.Concat` Span 拼接完成替换（零中间字符串）；项 15 新增的 `ApplyRandomIp` 三个头同款 IsMatch+Replace 双趟模式一并合并（5 参 Concat 无 Span 重载，头行先拼好再三段拼接）。验证：freq 3/3（含随机UA）、csrf 10/10 PASS。

## 二、架构技术债

### 10. 双模型双引擎入口收敛【P1 · 建议】 ✅已实施

- **为什么**：`ScriptTamperModel`（动态值脚本）与 `EncodeToolModel`（编码工具）承载同一 JS 执行能力，`ScriptTamperEngine` 为此维护 Tamper / TamperAsync / TamperStrict × 2 套重载（6 个公开入口），语义重复、新增脚本能力要改两处。
- **如何优化**：落点 `Bypass/ScriptTamperEngine.cs`。抽统一执行视图（如 `ITamperItem { Name; Builtin; Key; Code; }`，两模型各自实现），引擎只留一套三个入口；Builtin 解析统一走 EncodeToolRegistry（目前 ScriptTamperModel 走 BuiltinTampers、EncodeToolModel 走 EncodeToolRegistry，两套注册表也是重复）。
- **是否建议**：✅ 建议，但单独排期。涉及模型持久化字段兼容（反序列化不能破坏旧 lastconfig.json），改动面中等。
- **实施记录**（2026-09-28）：新增 `ITamperItem` 接口（`Key` 在 ScriptTamperModel 上显式实现返回 null，不参与序列化，旧配置兼容），两模型各自实现；引擎公开入口收敛为 Tamper/TamperStrict/TamperAsync 一套三个，内部统一 `ExecuteItem`——内置按 Key（空则 Name）解析 EncodeToolRegistry、自定义走 QuickJS。附带收益：EncodeToolRegistry 是 BuiltinTampers 超集（31 个 tamper 全转发），旧内置 tamper 项自动吃到更优实现（space2dash/space2hash/equaltolike）。

## 三、能力增强（对标 sqlmap，非性能项）

### 14. chunked 随机多块发送【能力 · 建议】 ✅已实施

- **为什么**：当前 `ApplyChunked` 把 body 作为**单块**发送（一个长度行 + body + 结束符），仅改变了传输编码形式。sqlmap 的 chunked 是把 body 切成**随机大小多块**（2-6 块），且切点可落在 SQL 关键字中间——WAF 对单块 body 做重组检测的成本很低，绕过效果差一档。这是能力面与 sqlmap 差距最大的一项。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` 第 337-360 行。body 按随机长度（可配置范围，默认 10-50 字节）切片，逐块输出 `<hex>\r\n<data>\r\n`，结束符 `0\r\n\r\n` 不变；注意 Content-Length 剔除逻辑已具备，切片只在 body 层做，不触碰 Encode 块语义。
- **是否建议**：✅ 建议。绕过能力直接增强，实现约 30 行，可配开关"随机分块大小"。
- **实施记录**（2026-09-28）：body 按 ChunkMinSize=10/ChunkMaxSize=50 随机字符数切片（切点对齐 UTF-16 字符边界不拆代理项对），每块按 UTF-8 字节数计长输出 `<hex>\r\n<data>\r\n`，StringBuilder 一次拼装，结束符不变。分块范围暂为内置常量，未开放 UI 配置（需要时再加）。

### 15. 随机源 IP 头（X-Forwarded-For / X-Real-IP）【能力 · 可选】 ✅已实施

- **为什么**：随机指纹目前仅 UA。部分 WAF/网关按 IP 限速或封禁，伪造客户端 IP 头是 sqlmap 常见绕过手段（--random-ip 类）。
- **如何优化**：ByPassConfig 增加开关 + BypassPlan 快照字段，ApplyPerRetryAsync 增加 Stage（与随机 UA 同层）：存在头则替换、不存在则插入到头区末尾；IP 池支持 CIDR/随机生成。
- **是否建议**：🔶 可选。对授权测试场景有效，但伪造头可能干扰目标日志审计，默认关闭。
- **实施记录**（2026-09-28）：新增 `RandomIpEnabled` 开关（默认关），ApplyPerRetryAsync Stage5.5 `ApplyRandomIp`：每轮重试生成随机公网观感 IPv4（首段 1-223、末段 1-254），对 X-Forwarded-For / X-Real-IP / Client-IP 三个头逐个"存在则替换、不存在则追加到头区末尾"（预编译正则，仅作用于头区不触碰 body）。UI 开关放在防护绕过-UA池页 subhead（随机UA 旁）。

### 16. HPP 扩展（body 位 + 参数名大小写混淆）【能力 · 可选】 ✅已实施

- **为什么**：当前 HPP 仅处理 Query 位且只按 %20 拆分；urlencoded body 位同语义未覆盖（注释里以 Content-Length 一致性为由跳过——但 FixContentLength 已具备，理由已不成立）；参数名大小写混淆（id → iD/Id）是另一类低成本 WAF 绕过。
- **如何优化**：落点 `Bypass/BypassPipeline.cs` ApplyHpp。body 位复用同一拆分逻辑后调 FixContentLength 收敛；大小写混淆作为独立开关在计划层实现。
- **是否建议**：🔶 可选。场景较窄，优先级低于第 14 项。
- **实施记录**（2026-09-28）：① HPP 正则前缀 `[?&]` 扩为 `[?&\n]`（\n 兼容 body 首参数位），替换后统一调 `StringReplace.FixContentLength` 收敛（GET 无此头时空操作）；② 新增 `ParamCaseRandEnabled` 开关（默认关）+ `ApplyParamCaseRand` Stage：注入参数名逐字符随机大小写，IgnoreCase 键控缓存正则保证命中已混淆形态，每轮重试重新随机（每逻辑请求复位后重算，不叠加）。UI 复选框放在防护绕过-协议级绕过 GroupBox（HPP 与 chunked 之间）。

## 四、不建议做的

| 项 | 原因 |
| --- | --- |
| ReplaceSteps 合并为单次扫描（Aho-Corasick 等） | 替换语义严格按列表顺序（前项产物可被后项再替换），合并改变语义；且替换项数量小、Encode 块短，当前开销可忽略 |
| 报文脚本并行执行 | 链式语义（后项输入=前项输出），不可并行 |
| QuickJS 换 V8/Node 外部进程 | 池化后单次调用微秒级，跨进程 IPC 反而更慢；QuickJS 静态链接零依赖是当前最优解 |
| 缓存 Token 抓取结果（TTL 复用） | CSRF token 普遍一次性失效，缓存会引入隐蔽失败；正确性优先于省一次往返 |
